<h2 id="lde-primer">先修知识：这份程序测的是什么？</h2>

系统调用让当前进程进入内核处理请求，完成后可以直接回到这个进程。上下文切换则让 CPU 停下一个进程，改为运行另一个进程。**一次系统调用不必伴随一次进程切换。**

本程序比较三组实验：

| 实验 | 一次迭代做什么 | 主要观测 |
| --- | --- | --- |
| read_zero | 零字节 read | 该系统调用路径及封装、循环的平均成本 |
| pipe_pair | 同一进程向管道写 1 字节，再自己读回 | 不需要另一进程回应的管道操作参照 |
| ping_pong | 父发请求、子收请求并回应、父收到应答 | 管道读写、唤醒、调度及进程交接的整体成本 |

```text
main：解析参数 → 绑定 CPU → 探测两种计时器
                                 ↓
                           重复 7 轮实验
                零字节 read → 单进程管道 → 双进程往返
                                 ↓
                         输出 CSV，成功结束
```

每项实验先准备、预热，再用两次读钟夹住大量重复操作；循环里不打印。不为每一次操作单独读钟，是为了摊薄计时器自身的影响。

### 描述符、地址和数据：先分清三件事

| 写法 | 它是什么 | 在本程序中做什么 |
| --- | --- | --- |
| `fd`、`read_fd`、`write_fd` | 保存描述符的整数 | 告诉内核操作哪一个文件或管道端点 |
| `channel[0]` / `channel[1]` | 数组里保存的读端/写端描述符 | 同进程管道参照；0、1 是数组下标，不是实际描述符值 |
| `outbound[1]` → `outbound[0]` | 父→子的管道两端 | 传请求 |
| `inbound[1]` → `inbound[0]` | 子→父的管道两端 | 传应答、ready 和最后的统计 |
| `token` | 局部字符变量 | 保存一个实际字节，内容为感叹号 |
| `&token` | 当前进程中变量的地址 | 指定从哪里取数据或把收到的字节放在哪里 |
| `stdout` / `stderr` | C 的输出流 / 错误流 | 打印测量数据与错误，不是 CPU 编号或管道下标 |

```text
父：outbound[1] ──请求──→ outbound[0]：子
父：inbound[0]  ←──应答── inbound[1] ：子
```

父关闭 outbound[0]、inbound[1]；子关闭 outbound[1]、inbound[0]。两边各自保留所需端点。描述符表独立，但引用同一条内核管道，所以一方写入的数据能被另一方读到。

<h2 id="token-flow">重点问答：第 82、88 行的两个 token 为什么能得到同一个值？</h2>

它们是两个独立的局部变量，不会因为名称相同而自动共享。发送函数先把自己的变量赋为感叹号，write 将该字节送进管道；接收函数声明自己的变量后，read 把管道里的字节写入它的地址。

```text
发送函数的局部变量             内核管道             接收函数的局部变量
  token = '!'   ──write──→      字节 '!'      ──read──→    token = '!'
```

第 88 行刚声明的 token 没有初始化，程序不会立刻使用这个未确定的值；下一行必须完整读取 1 字节后才检查它。读写失败会结束当前进程，不会把失败当作收到通知。

**管道传递的是字节内容，不是变量本身、名字或地址。**`&token` 只告诉各自那次系统调用从哪里取、往哪里放。把变量改名为 outgoing 和 incoming，效果仍然一样。即使这两个函数在同一进程中调用，它们也不是靠同名局部变量传值。

另一个容易混淆的细节：`transfer(..., 1, 1)` 的倒数第二个 1 是字节数，最后一个 1 表示写；`transfer(..., 1, 0)` 的最后一个 0 表示读，不是“读标准输入 0”。真正的目标由第一个 fd 参数决定。

```c
/* A closed peer is an error, not a successful zero-byte notification. */
static void transfer(int fd, void *buffer, size_t bytes, int writing)
{
    char *position = buffer;
    while (bytes != 0) {
        ssize_t n = writing ? write(fd, position, bytes) : read(fd, position, bytes);
        if (n < 0 && errno == EINTR) continue;
        if (n < 0) die(writing ? "pipe write" : "pipe read");
        if (n == 0) {
            fprintf(stderr, "Unexpected pipe EOF/zero progress\n");
            exit(EXIT_FAILURE);
        }
        position += n;
        bytes -= (size_t)n;
    }
}

```

### <a class="cpu-permalink" href="#lde-L63" aria-label="此步骤的永久链接">#</a> 读或写指定数量的字节，直到完成

transfer 的参数是目标 fd、数据地址、总字节数和读写开关。void * 可指向不同类型的数据，赋给 char * 后可按字节移动。条件表达式根据 writing 选择 write 或 read。

系统调用可能短读、短写，因此 n 成功后让位置向后移动 n、剩余长度扣除 n，再处理剩余部分。EINTR 重试，其他负数报错。

这里 n=0 是错误：调用者约定必须得到指定字节，未收齐就 EOF 表示对方没有完成协议。它与“读到 EOF 就正常结束”的文件复制程序约定不同。

static void null_reads(int fd, uint64_t iterations)
{
    char unused;

<h2 id="results">9. 实测结果：看数量级，也看测量含义</h2>

下面复用 **2026-10-28 21:59（UTC+8）** 的原始实验，不是本次排版时新测的数据。环境为 AMD Ryzen 7 8845H、WSL2 Linux 6.18.33.2、GCC 15.2.0，双方绑定 CPU 0。每轮 200000 次往返、2000000 次零字节 read，共 7 轮。

| 指标 | 7 轮最小值 | 中位数 | 最大值 |
| --- | ---: | ---: | ---: |
| 零字节 read，ns/次 | 205.07 | 206.92 | 219.71 |
| 同进程管道写+读，ns/对 | 734.42 | 742.36 | 816.47 |
| 双进程往返，ns/轮 | 4676.25 | 4737.33 | 5230.68 |
| 往返的一半，ns/次交接估计 | 2338.13 | 2368.67 | 2615.34 |

计算方式：

```text
平均零字节读取成本 = 读取批次总纳秒 / read 次数
平均往返成本       = 往返批次总纳秒 / N
每次交接相关估计   = 往返批次总纳秒 / (2N)
```

中位数 4737.33 ns 的一半约为 **2.37 µs**。每轮有父 write/read 和子 read/write 共四次管道系统调用、通常两次进程交接。这是小工作集下的切换相关估计，包含管道、唤醒、调度和循环，不是单独保存/恢复寄存器的纯成本。

每轮父子主动与被动切换合计为 400001～400049，与期望 2N=400000 接近。计数可能含与其他任务的切换，WSL 宿主暂停虚拟 CPU 也未必反映为客体计数，所以“接近”是支持证据，不是精确追踪。

### 为什么要批量，而不是只测一次？

gettimeofday 的 200000 对样本中，195989 对差值为零，最小正差值为 1000 ns；单调 RAW 时钟的相邻差值 p50 为 20 ns，标称分辨率为 1 ns。这三个量不等价，更不能说明绝对准确度。

单次 read 约 207 ns，直接用微秒级输出看它很容易得到零。这里将 200 万次操作合并，批次约 0.41～0.44 秒；往返批次约 0.94～1.05 秒，再除以次数。只有首尾读钟，才能摊薄读钟自身与量化的影响。

### 如何理解参照与限制？

同进程管道约 742 ns/对，说明通信本身就有成本；它没有跨进程的相同阻塞、唤醒与缓存路径，因此不直接从往返/2 扣掉它后宣称剩余的是精确切换成本。

CPU 绑定只约束位置，不排除其他进程，也不能独占 SMT 核的执行资源。大工作集、冷缓存、不同内核与宿主负载都可能改变结果。这份实验没有外部标准时钟，不验证绝对准确度；不需要为了纳秒单位就直接使用 rdtsc。
