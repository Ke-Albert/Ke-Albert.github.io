# LDE：测量系统调用与进程上下文切换

本作业实现 OSTEP Limited Direct Execution 的测量实验：检查计时器、批量执行零字节 read，再用两个绑定同一逻辑 CPU 的进程进行管道往返通信。

本机 7 轮实测的中位数：**零字节 read 约 207 ns/次；管道往返约 4.74 µs/轮；T/(2N) 得到约 2.37 µs/次的切换相关开销估计。**后者包含管道操作和调度等成本，不是单独保存/恢复寄存器的耗时。完整数据见 [结果报告](results/summary.md)。

## 复现

需要 Linux、GCC、Make、Python 3。无需 root，无需额外 Python 包。

从仓库根目录执行：

```sh
make -C cpu-lde
make -C cpu-lde test
make -C cpu-lde run
```

`run` 将原始数据打印到终端。生成报告并写入 results（会更新该目录中的同名测量文件）：

```sh
make -C cpu-lde report
```

单独指定参数或另存一次实验，避免覆盖本次记录：

```sh
./cpu-lde/lde_bench --help
./cpu-lde/lde_bench --cpu 0 --iterations 200000 --syscalls 2000000 --trials 7
python3 cpu-lde/run_experiment.py --output-dir results/recheck -- --trials 5
```

自动选择当前允许 CPU 集合中的第一个编号，不假设 CPU 0 永远可用。显式指定不在允许集合中的 CPU 会报错。CPU 集合使用 Linux 固定大小 cpu_set_t；超出 CPU_SETSIZE 的大规模机器需改用动态 CPU 集合，本实验环境有 16 个逻辑 CPU。

## 1. 先检查计时器

### gettimeofday 的单位不是它的实际准确度

gettimeofday 返回 Epoch 起的秒和微秒。本实验重复 20 万次“读两次时间戳，计算差值”，输出：零差值次数、负差值次数、最小正差值、p50/p90/p99 和最大差值。每一对读钟紧挨着进行，样本存储和统计放在两次读钟之后。

本次约 98% 的差值为 0，最小正差值为 1000 ns，即 1 µs。这不表示调用没有成本，也不能据此证明时钟绝对准确到 1 µs。微秒输出会把更短的间隔量化掉，极端差值还可能包含被抢占的等待。

gettimeofday 是墙上时间，可能受校时影响。因此正式耗时采用 CLOCK_MONOTONIC_RAW，同时也测量该时钟的相邻读钟间隔。它的 clock_getres 标称分辨率为 1 ns，本次最小正间隔 10 ns、p50 为 20 ns。**标称分辨率、相邻读钟间隔、读钟调用成本和绝对准确度是不同概念。**没有外部参考时钟，本实验不声称验证了绝对准确度。

### 为什么要批量计时

正式循环只在批次开始和结束各读一次时钟，不在每次 read 或每次切换时读钟。默认 200 万次 read 的批次持续约 0.41～0.44 秒，20 万次往返持续约 0.94～1.05 秒，远大于微秒级量化与几十纳秒读钟间隔。

即使按 1 µs 量级的端点量化估算，对 0.41 秒批次的影响也只有百万分之几；这只是计时量化的量级分析，不是总体误差界。后台进程、调度、频率和虚拟化更可能主导波动。为了避免把宿主 TSC 频率/指令序列化问题带入作业，不需要直接使用 rdtsc；批量单调时钟足够分辨本次目标。

## 2. 测系统调用：零字节 read

程序先只读打开 /dev/null，预热，再循环调用：

```c
read(fd, &unused, 0);
```

循环内不打印。检查返回值必须为 0；中断则重试，其他错误立即退出。计时之外关闭描述符。

计算：

```text
每次零字节 read 的平均耗时 = 批次总时间 / read 次数
```

read 仍走标准库的系统调用封装，0 字节避免实际搬运数据。这个结果包括封装、进入/离开内核、内核的该条 read 路径、循环与返回检查，**不是所有系统调用共有的固定成本**。它不包括一个阻塞 read 所等待的数据时间。计时器本身在现代 Linux 上可能通过 vDSO 读取，并不能因此拿读钟调用替代 read 来测内核入口。

发生 EINTR 时实际尝试次数可能比设定次数稍多；代码支持重试，但没有为实验主动发送信号。

## 3. 单进程管道参照

同一进程创建一条管道，每轮先写 1 字节，再读回这个字节。数据在 read 前已经存在，不需要另一个进程回应；每轮字节都读空，不会持续填满管道。

```text
当前进程 write → 管道 → 当前进程 read
```

这给出“一次管道写+读”的参照耗时，仍可能被其他进程抢占。它不是可精确扣除的纯系统调用成本：没有跨进程唤醒和阻塞，缓存状态及内核路径也不同。因此报告展示它，但不直接相减后宣称剩下的是纯切换成本。

## 4. 两个进程在同一 CPU 上往返

### 为什么需要两条管道

一条管道只提供单向字节流。父→子、子→父分别使用一条，避免同一端误读自己发出的字节：

```text
父进程                      子进程
outbound[1] ───────────────→ outbound[0]
              1 字节请求
inbound[0]  ←─────────────── inbound[1]
              1 字节应答
```

父进程关闭 outbound[0]、inbound[1]；子进程关闭 outbound[1]、inbound[0]。保留端点均会在结束时关闭。

### 为什么必须绑定同一个逻辑 CPU

先查询允许 CPU 集合，再用 sched_setaffinity 将父进程绑定到其中一个逻辑 CPU。随后 fork，子进程继承同样的 CPU 亲和性。双方各检查集合恰好只有一个 CPU，且 sched_getcpu 返回选定编号；逐轮结果也保存双方 CPU 编号。

这里要求同一个**逻辑 CPU**，不是仅在同一个物理核的两个 SMT 线程上。如果分属两个逻辑 CPU，双方可能并行执行，测量会混入跨核通信，而不再对应同一 CPU 停下一个进程、恢复另一个进程的目标。

### 一轮如何形成两次交接

```text
父：write 请求 → read 应答，尚无数据则阻塞
                   ↓ 父切换到子
子：read 请求 → write 应答 → read 下一请求，尚无数据则阻塞
                   ↓ 子切换到父
父：read 返回，开始下一轮
```

实现使用每轮 1 字节、同步请求/应答。写入唤醒读者时也可能发生抢占，具体主动/被动切换分配由调度决定；不能只数“主动切换”就认定所有交接。

### 计时边界

每轮试验都先建管道、fork、检查 CPU 并做 1 万轮预热。子进程取初始资源统计，再发一个独立 ready 字节；父进程读到 ready 后才开始正式计时。

父进程的计时范围仅包含 N 次 write 请求/read 应答。收到最后一份应答后立即停止计时；接收子进程统计、关闭描述符和 waitpid 回收都在计时外。子进程用 _exit，避免复制父进程的标准输出缓冲。

父子各用 getrusage(RUSAGE_SELF) 记录 ru_nvcsw（主动切换）、ru_nivcsw（被动切换）增量。子进程的统计还包含 ready 边界，父进程的统计包括计时端点，因此它们与严格计时区间略有差异，不把计数当成完全一致的硬件事件追踪。

### 计算与验证

```text
单轮往返耗时       = T / N
每次切换相关的估计 = T / (2 × N)
切换计数核对       = (父主动 + 父被动 + 子主动 + 子被动) / (2 × N)
```

7 轮中每轮 N=200000，切换数为 400001～400049，计数比接近 1。说明该运行确实发生了预期数量的交替切换；计数还可能包括与其他任务的交接，不是“恰好只切到对方”的证明。

## 5. 结果与边界

本次机器为 AMD Ryzen 7 8845H，Linux 6.18.33.2-microsoft-standard-WSL2，GCC 15.2.0，绑定 CPU 0。准确的编译器版本、时钟源和完整命令以 [环境记录](results/environment.json) 为准。

| 指标 | 7 轮中位数 | 含义 |
| --- | ---: | --- |
| 零字节 read | 206.92 ns | 该 read 路径连同封装与循环的平均成本 |
| 同进程管道写+读 | 742.36 ns | 一对不需要进程间应答的管道操作参照 |
| 双进程管道往返 | 4737.33 ns ≈ 4.74 µs | 两次交接与四次管道系统调用的整体成本 |
| 往返 / 2 | 2368.67 ns ≈ 2.37 µs | 每次切换相关的平均开销估计 |

每次往返有父 write/read、子 read/write，共四次管道调用，不能把整个 RTT 当成一次切换。没有直接观测内核中保存/恢复寄存器的那一小段，不能把 2.37 µs 称为其纯成本。

该实验测的是小工作集下、热缓存附近、两个简单进程之间的交接。大型程序地址空间、缓存失效、额外线程或不同 IPC 机制都会改变结果。CPU 亲和性不独占 CPU；WSL2 宿主机调度可能暂停虚拟 CPU，而未反映为客体进程的切换计数。这里的数字适用于本次环境，不能作为所有机器的常数。

测试只验证协议、计时计算、CPU 约束和错误参数，不断言某个固定速度。性能结果使用多轮最小值、中位数、均值、最大值，而不是只挑一轮最佳值。
